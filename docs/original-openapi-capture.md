# Original OpenAPI capture receipts

The original SDK build starts `io.fireflysoftware.masters.web.openapi.OpenApiGenApplication`, uses Springdoc to fetch the running application's YAML, stops that application, and invokes the existing OpenAPI Generator in the dependent SDK module. The SDK and specification remain generated by that lifecycle.

An optional `capture-original-openapi-receipt` profile adds response evidence to this same original producer. It does not replace the producer, introduce an alternative specification, change the generator, or run a second application. The receipt filter and its configuration live exclusively in the Web module's test classpath. The production application and packaged business services do not include them.

## Default behavior and explicit activation

Normal builds retain their existing behavior. Capture is disabled unless the explicit Maven profile is selected. Within the application, both the `openapi-gen` Spring profile and `firefly.openapi.capture.enabled=true` are required. No capture properties are resolved and no writer is constructed when capture is disabled.

The opt-in Maven profile appends four arguments to the existing `openapi-start` execution and adds the matching `X-Firefly-OpenAPI-Capture` request header to the original Springdoc plugin configuration. It preserves the existing discovery arguments and lifecycle execution identities.

| Input | Requirement |
| --- | --- |
| `firefly.openapi.capture.directory` | A newly allocated existing directory dedicated to this one build invocation. Its actual POSIX permissions must be `0700`; neither it nor any path component may be a symbolic link. `receipt.json` must be absent. |
| `firefly.openapi.capture.source-sha` | The exact reviewed 40-character lowercase hexadecimal source commit, supplied and independently checked by the outer build gate. |
| `firefly.openapi.capture.invocation` | A fresh invocation identifier containing 32–128 ASCII letters, digits, underscores, or hyphens. The outer gate must retain its expected binding privately. |

The outer qualification runner owns directory allocation, exact source and invocation binding, original JVM identity, port ownership, finite runtime budget, capture/client identity, and cleanup. Selecting this profile alone does not satisfy those responsibilities. The shared release workflow has not adopted a complete owner policy or post-build verifier yet; the existing release wrappers are deliberately unchanged until those contracts and the full test suite are qualified.

Springdoc Maven plugin 1.4 supports the request-header map used here. Its actual plugin descriptor does not expose the `failOnError` setting shown by newer plugin documentation. This implementation does not rely on an unsupported flag. A future reviewed post-build verifier must fail when the expected fresh receipt is missing, invalid, or mismatched, even if the plugin logged an error while leaving an older specification on disk.

## What the receipt establishes

Only `GET /v3/api-docs.yaml` with exactly one matching invocation header may claim the capture. Health requests and other routes do not consume it. A second matching capture is refused. The filter observes the actual original response buffers without changing their read positions or collecting an unbounded copy of the body.

A receipt is written only after all response body publishers and flush parts complete, the response is committed, the outer response chain completes successfully, status is 200, the content type is an accepted YAML type, and 1–4,194,304 response bytes have been observed. A successful writer that cancelled a body after the first chunk does not qualify. Cancellation, body/chain errors, empty/error responses, and oversized responses cannot create a success receipt. Refused and discarded pooled buffers are released.

The exclusive file uses POSIX mode `0600` and directory-relative secure file operations with no symlink following. A preexisting output is never replaced, including an output created after filter construction. Unsupported secure-directory operations fail closed. A write failure may leave an incomplete private file; that file is not valid proof and must not be overwritten or repaired into success.

The bounded JSON contains only:

- Schema number, exact supplied source commit, and a SHA256 digest of the invocation identifier.
- Original producer application identity and the exact captured route.
- Successful HTTP status, response byte count, SHA256 of the observed response bytes, and `RESPONSE_COMPLETED` state.

It contains no raw specification body, raw invocation identifier, environment, process ID, argv, token, classpath, database rows, or provider data. Server-side response completion is not a claim that a remote consumer received or accepted the bytes.

## Required follow-through before release adoption

A source/invocation-bound server receipt is one prerequisite. The final owner verifier must additionally bind the fresh Springdoc output to this response, validate the entire actual typed specification, prove original Generator execution and generated source/API/model inventory, compare packaged SDK classes and both specification aliases, retain typed compile/wire checks, and enforce original producer ownership/cleanup. It must reject stale, missing, partial, ambiguous, or changed output. The shared release publisher's bounded proof schema is a separate final interface; this receipt does not set its `original_producer` or `original_generator` acceptance booleans.

The owner policy must inventory all actual reactor artifacts and the full zero-skip Surefire/Failsafe suite. Prior selected original tests are historical evidence, not a substitute for that full inventory. Current SDK runtime integrations require actual owned Docker/PostgreSQL and forked application qualification. Published parent `26.10.6` remains immutable; a corrected parent version and cold released-dependency consumer must be qualified separately.

The source tests exercise real Spring WebFlux mock exchanges and JDK filesystem operations without starting a server, database, container, issuer, or policy engine. They cover completed/chunked response hashing, profile/default behavior, invocation mismatch, partial writer completion, cancellation, errors, bounds, pooled-buffer release, private output permissions, symlink refusal, and exclusive output. These tests do not establish a new original Maven/producer run, actual network capture, full release suite, artifact publication, complete financial journey, or DORA acceptance.
